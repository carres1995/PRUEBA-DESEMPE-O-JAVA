# 🗺️ User Guide — SDD Boilerplate Assets

> **Objective:** Learn how to use the 3 inputs (`CONSTITUTION.md`, `SPEC_TEMPLATE.md`, `BusinessRuleSpecTemplateTest.java`) to develop Java SE features with AI assistance, following the Specification-Driven Development (SDD) workflow.

---

## 📦 What do you have?

| File | Role | When to use it? |
|---------|-----|-------------------|
| `init_sdd_project.sh` | **The project generator** — creates the entire Maven scaffolding in one command | Once at the start of the project |
| `CONSTITUTION.md` | **The rules of the game** — the AI reads it to know WHAT patterns to follow | Always. Attached to every AI prompt |
| `SPEC_TEMPLATE.md` | **The request template** — you fill it out describing WHAT you want | One copy for each new feature |
| `BusinessRuleSpecTemplateTest.java` | **The test mold** — the AI uses it to know HOW to structure tests | Reference. The AI replicates it internally |
| `SPEC_DEDUCTION_GUIDE.md` | **The deduction guide** — teaches you to extract specs from a prompt | Study. Read it before filling your first SPEC |

---

## 📍 Where do these files live?

This `sdd_assets/` folder is your **permanent toolkit** — never delete or move it. You generate new projects from here.

```
📂 sdd_assets/                         ← 🔒 YOUR TOOLKIT (Master Source)
├── init_sdd_project.sh                 ← Run from here
├── CONSTITUTION.md                     ← Copied to the new project
├── SPEC_TEMPLATE.md                    ← Copied to the new project
├── BusinessRuleSpecTemplateTest.java   ← Copied to the new project
├── SPEC_DEDUCTION_GUIDE.md             ← Copied to the new project
└── USER_GUIDE.md                       ← Your reference (not copied)
```

When you run the script, a **new independent project** is created with its own copies:

```
📂 MyProjects/
└── 📂 my-store/                        ← GENERATED PROJECT
    ├── pom.xml                         ← Generated by the script
    ├── README.md
    ├── .gitignore
    ├── sdd_assets/                     ← Copies to use with the AI
    │   ├── CONSTITUTION.md
    │   ├── SPEC_TEMPLATE.md
    │   └── BusinessRuleSpecTemplateTest.java
    └── src/
        ├── main/java/com/store/
        │   ├── config/ConnectionFactory.java
        │   ├── exception/ServiceException.java
        │   ├── model/ dao/ service/ controller/ view/
        ├── main/resources/sql/         ← Generated tables go here
        └── test/java/com/store/service/
```

> **Simple rule:** The toolkit generates projects. Inside each project, you work with the local copies.

## 🔄 Full Workflow (Step-by-Step)

---

### Phase 0: Prerequisites (ONCE per project)

> **Before touching any of the 3 SDD inputs, you need to have this ready.**

#### 0.1 — Installed Software

| Tool | Minimum Version | Verification |
|-------------|---------------|-------------|
| **JDK** | 17+ (LTS) | `java --version` |
| **Maven** | 3.8+ | `mvn --version` |
| **Git** | 2.x | `git --version` |
| **IDE** | IntelliJ / VS Code + Java Pack / Eclipse | Support for JUnit 5 |
| **DB Engine** | PostgreSQL, MySQL, or H2 | `psql --version` or equivalent |

#### 0.2 — Create Project (Automatic ⚡)

Use the `init_sdd_project.sh` script to generate EVERYTHING in a single command.
**Navigate first to where you want to create the project**, then run the script with its full path:

```bash
# 1. Go to the folder where you want to create your new project
cd ~/Documents/MyProjects/

# 2. Run the script using its full path
#    Syntax: <path-to-script>/init_sdd_project.sh <name> <package> [db] [ui]

# Examples:
~/path/to/sdd_assets/init_sdd_project.sh my-store com.store postgresql
~/path/to/sdd_assets/init_sdd_project.sh grading-system com.grades mysql javafx
~/path/to/sdd_assets/init_sdd_project.sh demo-app com.demo h2 swing
~/path/to/sdd_assets/init_sdd_project.sh my-web com.web postgresql web
```

> **💡 Tip:** To avoid typing the full path every time, you can create an alias in your terminal:
> ```bash
> # Add this to your ~/.bashrc or ~/.zshrc
> alias sdd-init='~/path/to/sdd_assets/init_sdd_project.sh'
>
> # Then just use:
> sdd-init my-store com.store postgresql
> sdd-init my-app com.app mysql javafx
> ```

**The script automatically generates:**

| Generated File | Content |
|-----------------|-------------|
| `pom.xml` | Java 17, JUnit 5, JDBC driver (per choice), H2 for tests, Surefire + UI dependencies |
| `ConnectionFactory.java` | Production connection + H2 test connection |
| `ServiceException.java` | Base exception for infrastructure errors |
| `MainView.java` / `MainFrame.java` / `HomeServlet.java` | Base UI file (only if the 4th parameter is passed) |
| `.gitignore` | Rules for Java, IDE, DB, logs |
| `README.md` | Project description with instructions |
| `sdd_assets/` | Copy of CONSTITUTION, SPEC_TEMPLATE, and BusinessRuleSpecTemplateTest |
| Full Structure | All folders by layer (model, dao, service, etc.) |
| Git | Initialized repository with initial commit |

```bash
# PostgreSQL
sudo -u postgres createdb my_store
# MySQL

```

```bash

mvn compile     # ← should say BUILD SUCCESS
mvn test        # ← should say BUILD SUCCESS (0 tests for now)
```

> **✅ All set → Proceed to Phase 1.**

### Phase 1: Prepare the Specification (YOU — no code)

```
📝 Estimated time: 10-20 minutes
```

**Step 1.** Copy `SPEC_TEMPLATE.md` and rename it:
```bash
cp SPEC_TEMPLATE.md SPEC_UserRegistration.md
```

**Step 2.** Open your copy and fill out ONLY these sections (without thinking about code):

| Section | What to write | Example |
|---------|-------------|---------|
| **Business Goal** | Who, what they need, for what | *"As a new user, I need to register an account, so that I can access the platform"* |
| **Hard Business Rules** | Rules the system MUST fulfill | `BR-001: Email must not be null or empty` |
| **Acceptance Criteria** | Given-When-Then scenarios | *"Given a user with null email, When register() is called, Then throw InvalidUserException"* |
| **Technical Notes** | Class and field names | `User.java` with fields: `id`, `name`, `email`, `password` |

**Step 3.** Delete scenarios that DO NOT apply to your feature.
> If your feature only has 4 business rules, leave only 4-5 scenarios (happy path + one validation per rule). Do not leave the 10 scenarios if you don't need them.

---

### Phase 2: Request Code from AI (YOU → AI)

```
📝 Estimated time: 2-5 minutes of prompting
```

**Step 4.** Open a conversation with the AI and attach TWO files as context:

```
📎 Attach: CONSTITUTION.md
📎 Attach: SPEC_UserRegistration.md (your filled spec)

Prompt:
"Following the attached CONSTITUTION.md and the SPEC_UserRegistration.md specification,
generate all the code in the order established in Section 1 (AI Workflow).

Ensure to include the UI Integration in the main file (Step 11).
⚠️ For Step 11, provide the COMPLETE Main file, with all its imports and updated Layout rules, without duplicating methods or cutting code snippets.
Use the package com.project."
```

> **💡 Tip:** The CONSTITUTION already tells the AI exactly what to do. You don't need to explain patterns, transactions, or try-with-resources — all of that is in the rules.

**Step 5.** The AI will generate the files in this order:

```
1. SQL DDL                       ← Generates table in resources/sql/
2. InvalidUserException.java     ← Exception
3. User.java                     ← Model (POJO)
4. UserServiceTest.java          ← Tests (10 or fewer, per your scenarios)
5. UserDao.java                  ← DAO (Pure JDBC)
6. UserService.java              ← Service (rules + transactions)
7. UserController.java           ← Controller (validates UI input)
8. UserView.java                 ← View (only if you filled the UI section)
9. MainView/MainFrame/index.jsp  ← UPDATED FILE (Step 11: Integration)
```

---

### Phase 3: Verify (YOU — execute and validate)

```
📝 Estimated time: 5-10 minutes
```

**Step 6.** Place the generated files in the package structure:
```
src/main/resources/sql/
└── user_table.sql

src/main/java/com/project/
├── exception/InvalidUserException.java
├── model/User.java
├── dao/UserDao.java
├── service/UserService.java
└── controller/UserController.java

src/test/java/com/project/
└── service/UserServiceTest.java
```

**Step 7.** Run the tests:
```bash
mvn test
# or
gradle test
```

**Step 8.** Verify that:

| ✅ Check | What to review |
|----------|------------|
| Tests pass | `BUILD SUCCESS` in the terminal |
| Correct architecture | DAO **does not** have `setAutoCommit` or `commit` |
| try-with-resources | All `PreparedStatement` and `ResultSet` are in `try(...)` |
| Transactions in Service | `setAutoCommit(false)` → `commit()` → `rollback()` only in Service |
| Constructor injection | Service receives DAO via constructor, does not create it internally |

---

### Phase 4: Commit (YOU — version control)

**Step 9.** Make commits following the SDD order:

```bash
git add SPEC_UserRegistration.md
git commit -m "docs(spec): add spec for user registration"

git add src/main/resources/sql/ src/main/java/com/project/exception/ src/main/java/com/project/model/
git commit -m "feat(registration): add User model, InvalidUserException and SQL schema"

git add src/test/
git commit -m "test(registration): add business rule tests for user registration"

git add src/main/java/com/project/dao/ src/main/java/com/project/service/
git commit -m "feat(registration): implement UserDao and UserService"
```

## 🚫 Common Errors

| ❌ Error | ✅ Solution |
|----------|-----------|
| Leaving 10 scenarios unfilled | Delete those that don't apply. Fewer empty scenarios = better AI output |
| Not attaching CONSTITUTION to the prompt | Without it, the AI doesn't know the rules. **Always attach it** |
| Asking only to "generate the Service" | Ask for the full flow. The AI needs to generate the test BEFORE the service |
| Editing code without updating the spec | If a business rule changes, update the spec first, then regenerate |
| Writing code before the spec | Stop. Fill the spec first. That is SDD principle #1 |

## 🔁 What if I need to modify an existing feature?

1. Open the existing spec (`SPEC_[Feature].md`)
2. Add/modify the affected Business Rules and Scenarios
3. Attach CONSTITUTION + updated spec to the AI
4. Prompt: *"The spec was updated. Regenerate ONLY the tests and the service for the marked changes."*
5. Run tests, validate, commit with `fix()` or `feat()`

## 📐 What if my feature is very simple (1-2 rules)?

Use a minimal spec. Example of a spec with only 2 scenarios:

```markdown
## 2. Hard Business Rules
| Rule ID | Rule Description | Error Behavior |
|---------|-----------------|----------------|
| BR-001  | Product name must not be empty | Throw InvalidProductException |

## 3. Acceptance Criteria
### Scenario 1 — Happy Path
Given a valid Product with name "Laptop"
When  the service method save() is called
Then  the product is persisted successfully

### Scenario 2 — Null Name
Given a Product with null name
When  the service method save() is called
Then  InvalidProductException is thrown
```

> That's enough. The AI will generate 2 tests, not 10. **Less is more when rules are few.**
